Looking at your code and at how Unitree's LiDAR protocol is typically implemented, I would not start by blaming the UDP socket. The fact that:

* you receive LiDAR packets correctly,
* `sendto()` does not raise an exception,
* but commands have no effect,

usually means **the command frame is malformed**, **sent to the wrong endpoint**, or **missing fields required by the protocol**.

## First thing I would verify: packet size calculation

Your frame builder assumes:

```python
HEADER_SIZE = 12
TAIL_SIZE = 12

packet_size = HEADER_SIZE + len(payload) + TAIL_SIZE
```

and creates:

```python
header = _FRAME_HEADER + struct.pack('<II', packet_type, packet_size)
```

which indeed gives 12 bytes.

But your tail is:

```python
tail = struct.pack('<II', crc, 0) + bytes([0x00, 0x00]) + _FRAME_TAIL
```

Let's count:

```text
crc             4
msg_type_check  4
reserve         2
tail            2
---------------
total          12
```

That part is consistent.

However, the protocol may define `packet_size` as:

```cpp
payload_size
```

instead of

```cpp
entire_frame_size
```

or

```cpp
header + payload
```

instead of

```cpp
header + payload + tail
```

This is probably the most common reason commands are silently ignored.

Add:

```python
print(
    f"type={packet_type}, "
    f"payload={len(payload)}, "
    f"frame={len(header+payload+tail)}, "
    f"packet_size_field={packet_size}"
)
```

and compare against packets emitted by the official SDK.

# Second likely issue: wrong USER_CMD value

You define:

```python
_CMD_STANDBY = 2
```

and send:

```python
struct.pack('<II', 2, 0)
```

for start.

Your comment says:

```python
# USER_CMD_STANDBY_TYPE (0 = start, 1 = standby)
```

but that may not be how Unitree encodes it.

Many Unitree protocols use:

```cpp
cmd_type = USER_CMD_STANDBY_TYPE
cmd_value = USER_CMD_ENABLE
```

or

```cpp
cmd_value = 0
cmd_value = 1
```

depending on firmware.

If the firmware changed, the command is accepted but ignored.

---

# Third likely issue: CRC mismatch

Your CRC implementation looks like standard CRC32:

```python
crc = 0xFFFFFFFF
...
return (~crc) & 0xFFFFFFFF
```

But Unitree sometimes uses:

```cpp
boost::crc_32_type
```

which yields a different finalization.

I would verify by computing CRC on an actual packet captured from the official SDK.

Add:

```python
print(hex(crc))
```

and compare against Wireshark captures.

---

# Fourth likely issue: msg_type_check field

You always send:

```python
struct.pack('<II', crc, 0)
```

meaning:

```python
msg_type_check = 0
```

But your parser shows:

```python
tail:
    crc32
    msg_type_check
```

I strongly suspect this field is not supposed to be zero.

Many Unitree packet formats put:

```cpp
msg_type_check = packet_type
```

or

```cpp
~packet_type
```

there.

Try:

```python
tail = struct.pack(
    '<II',
    crc,
    packet_type
)
```

instead of:

```python
tail = struct.pack(
    '<II',
    crc,
    0
)
```

This is actually one of my top suspects.

# Fifth likely issue: command payload structure

You currently send:

```python
payload = struct.pack('<II', cmd_type, cmd_value)
```

giving:

```text
8 bytes
```

But the SDK may define:

```cpp
struct UserCmdPacket
{
    uint32_t cmd_type;
    uint32_t cmd_value;
    uint32_t reserve;
};
```

or

```cpp
uint64_t cmd_value;
```

which would make your packet invalid.

I would compare against the C++ struct exactly.

# Sixth likely issue: wrong destination port

You send to:

```python
6101
```

because:

```python
port_lidar=6101
```

But many Unitree devices use:

```text
6101  -> data
6102  -> commands
```

or

```text
6201 -> data
6101 -> command
```

depending on firmware.

Because receiving works does not prove commands are sent to the correct port.

I would capture packets while using the official SDK:

```bash
sudo tcpdump -i eth0 host 192.168.1.62
```

or Wireshark.

Then check:

```text
destination port
```

of a successful stop command.

---

# Seventh likely issue: binding the command socket

You use a single socket:

```python
self.sock.bind((self.local_ip, self.receiving_port))
```

and then:

```python
self.sock.sendto(...)
```

from that same socket.

Some embedded systems expect commands from a specific source port.

You currently transmit from:

```text
192.168.1.100:6201
```

because the socket is bound there.

The official SDK may use:

```text
ephemeral source port
```

or

```text
6101
```

instead.

Try a dedicated command socket:

```python
self.cmd_sock = socket.socket(
    socket.AF_INET,
    socket.SOCK_DGRAM
)
```

without bind:

```python
def _send_command(self, frame):
    self.cmd_sock.sendto(
        frame,
        (self.lidar_ip, self.sending_port)
    )
```

---

# Eighth issue: you never check ACK

You commented out the most important debugging code.

Restore it.

```python
try:
    ack_raw, addr = self.sock.recvfrom(512)
    print("ACK raw:", ack_raw.hex())
except socket.timeout:
    print("No ACK")
```

If there is:

```text
No ACK
```

then:

* wrong port
* malformed packet
* wrong CRC

If there is:

```text
ACK status = CRC_ERROR
```

then CRC is wrong.

If there is:

```text
ACK status = HEADER_ERROR
```

then frame layout is wrong.

If there is:

```text
ACK status = SUCCESS
```

then the command format is correct and the problem is elsewhere.

---

# What I would do first

1. Capture traffic from the official SDK.
2. Compare byte-for-byte with your Python frame.
3. Verify:

   * packet_size field
   * CRC
   * msg_type_check
   * payload structure
   * destination port
4. Re-enable ACK parsing immediately.

I'd start by modifying `_build_frame()` like this:

```python
def _build_frame(packet_type: int, payload: bytes) -> bytes:

    packet_size = 12 + len(payload) + 12

    header = (
        _FRAME_HEADER
        + struct.pack("<II", packet_type, packet_size)
    )

    crc = _crc32(header + payload)

    tail = (
        struct.pack(
            "<II",
            crc,
            packet_type      # <- try this instead of 0
        )
        + b"\x00\x00"
        + _FRAME_TAIL
    )

    frame = header + payload + tail

    print("FRAME:", frame.hex())

    return frame
```

and then restoring ACK parsing. The ACK status will usually reveal the exact failure within a few packets.
